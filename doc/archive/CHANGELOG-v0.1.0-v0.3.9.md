





# v0.1.0 起源

**起源**

9月15日周二11:11

**ChatGPT 5.6的聊天框：**

我说：

> 帮我开发一个markdown编辑器吧。 我希望极速打开文件和非常轻量化。最好是C语言或者C++实现，你觉得如何？ 可以先做浏览先不做编辑。名称叫做MDYe，你觉得如何？

**MDYe** 我觉得可以，而且挺适合这个项目。

它有几个优点：短、好记、像工具名，而且一眼能看出和 Markdown 有关系。更重要的是，它和你现在已有的 **YeImageViewer、Yetool** 这类命名也比较统一，慢慢可以形成自己的 “Ye” 工具系列。

我建议正式名字就定：

**MDYe — Lightweight Markdown Viewer**

中文可以叫：

**MDYe — 极速轻量 Markdown 阅读器**

第一阶段定位可以非常明确：

> 双击即开，专注阅读。
> 一个原生 C++ 实现的极速、轻量 Markdown Viewer。

项目结构我甚至建议一开始就保持极简：

```
MDYe/
├─ src/
│  ├─ main.cpp
│  ├─ app.cpp
│  ├─ window.cpp
│  ├─ markdown.cpp
│  ├─ renderer.cpp
│  └─ file_loader.cpp
├─ include/
├─ assets/
├─ tests/
├─ CMakeLists.txt
├─ build.bat
└─ README.md
```

技术路线暂定：

**C++17 + Win32 + md4c + DirectWrite/Direct2D**

而不是 WebView2。

这样我们的目标就可以很激进：

- EXE 尽量 **1–3 MB**
- 无安装依赖或极少依赖
- 不需要 WebView2
- 不启动本地 HTTP Server
- 双击 `.md` 直接打开
- 小文件争取 **100 ms 级出窗口**
- 10 MB、50 MB Markdown 也不能明显卡死
- 内存尽量控制在几十 MB
- Windows 10 / 11 原生支持
- 第一版只读，不做编辑

我会把 **MDYe v0.1.0** 定义成一个纯 Markdown Viewer，而不是一开始做成编辑器。先把“**打开速度 + 阅读体验**”这两件事做到极致，后面再加编辑。


我说：

> mdview 有个我问题是打开md界面会有1-2s的空白，实际应该在加载文件，而我想做的就是双击立马打开，可以达到emeditor的效果，或者可以分段加载那种效果。


对，这个目标我非常赞成，而且这会直接决定 **MDYe 的架构不能走 mdview 那种“文件 → Markdown → HTML → WebView”的完整渲染链路**。

你要的不是单纯“启动快”，而是：

> **双击 `.md` 后，窗口和第一屏内容几乎立即出现；后面的内容可以继续加载。**

这和 EmEditor 的思路更接近。

我建议把它直接定成 MDYe 最重要的设计原则：

## MDYe：First Screen First

不要：

```
双击文件
   ↓
读取整个文件
   ↓
解析整个 Markdown
   ↓
生成完整页面
   ↓
布局整个页面
   ↓
显示窗口
```

因为哪怕其中每一步只要 200~300ms，加起来就很容易出现你在 mdview 里看到的 **1~2 秒白屏**。

MDYe 应该这样：

```
双击 .md
   ↓
立即创建主窗口
   ↓
映射文件
   ↓
读取/解析第一屏附近内容
   ↓
立即显示正文
   ↓
━━━━━━━━━━━━━━━━━━━━
后台继续：
   ↓
扫描剩余文件
   ↓
建立段落索引
   ↓
解析 Markdown
   ↓
建立标题目录
   ↓
加载图片
   ↓
语法高亮
```

也就是说：

> **永远不要等整个 Markdown 文档准备完成才显示。**

# 我建议甚至不要用 RichEdit

刚才我提到：

```
C++ + Win32 + RichEdit / DirectWrite
```

如果现在明确要求：

> 像 EmEditor 一样极速打开超大 Markdown

我会进一步改成：

```
C++20
Win32
DirectWrite
Direct2D
自定义 Markdown Layout / Virtual Document
```

也就是：

**不用 RichEdit。**

原因很简单。

RichEdit 很方便，但它天然倾向于：

```
把整个 document 交进去
↓
内部管理全文
↓
布局/格式化
```

对于普通 100 KB、1 MB 文件问题不大。

但以后如果你打开：

```
10 MB
50 MB
100 MB
甚至 500 MB Markdown
```

我们自己控制虚拟化会漂亮得多。

# MDYe 应该把 Markdown 看成“很多块”

比如这个文件：

````
# PCIe Bring-up

这是第一段内容。

## Link Training

一些内容。

```cpp
void InitPCIe()
{
}
````

## HDMA

| Test | Result |
| --- | --- |
| H2D | Pass |

````
MDYe 内部不要马上把它变成一个完整 document。

先变成：

```text
Block 0
Heading H1
offset: 0
length: 18

Block 1
Paragraph
offset: 20
length: 30

Block 2
Heading H2
offset: 52
length: 20

Block 3
Paragraph
...

Block 4
Code Block
...

Block 5
Heading
...

Block 6
Table
...
````

形成一个非常轻的数据结构：

```
struct Block {
    uint64_t offset;
    uint32_t length;
    BlockType type;
};
```

甚至一开始：

```
type
```

都可以先不知道。

先只有：

```
offset
length
```

需要显示的时候再解析。

这叫：

# Lazy Parsing

按需解析。

# 最关键的一点：只布局屏幕上看到的内容

假设一个 Markdown 有：

```
100000 行
```

用户打开以后屏幕实际上只看到：

```
40 行
```

那为什么要渲染 100000 行？

我们只做：

```
当前屏幕

        ↑
   前 2 屏缓存
━━━━━━━━━━━━
   当前 1 屏
━━━━━━━━━━━━
   后 2 屏缓存
        ↓
```

也就是：

```
Viewport Virtualization
```

例如：

```
文档

Block 0
Block 1
Block 2
...
Block 283
Block 284      ← 当前附近
Block 285      ← 当前屏幕
Block 286      ← 当前屏幕
Block 287
Block 288
...
Block 10000
```

只真正创建：

```
DirectWrite TextLayout
```

给：

```
Block 280 ~ 292
```

其他块只是：

```
offset
长度
估计高度
```

# 这样大文件和小文件实际上走同一个机制

比如打开一个：

```
README.md
70 KB
```

实际上瞬间全部扫描完。

打开：

```
notes.md
8 MB
```

第一屏先显示，后面后台扫描。

打开：

```
AI-chat-history.md
80 MB
```

依然：

```
第一屏立刻显示
```

用户不会感受到：

> 软件正在解析 80 MB 文件。

这才是我认为 MDYe 有价值的地方。

# 文件本身也不要完整读进内存

Windows 提供：

```
CreateFileW()
CreateFileMappingW()
MapViewOfFile()
```

我们可以直接做：

```
MD File
   ↓
Memory Mapping
   ↓
Virtual Document
```

例如：

```
100 MB markdown
```

并不意味着：

```
fread 100 MB
+
复制 string 100 MB
+
Markdown AST 200 MB
+
HTML 300 MB
+
WebView DOM...
```

MDYe 可以基本保持：

```
文件映射
+
Block Index
+
当前页面 Layout
```

这对内存特别有利。

# 一个非常重要的细节

我不建议为了“极速”而让用户看到这种效果：

```
# hello

**world**
```

先显示原始 Markdown：

```
# hello
**world**
```

然后突然跳成格式化页面。

那会有明显闪烁。

更好的办法是：

第一次同步解析的数据量很小，例如：

```
64 KB / 128 KB
```

只解析第一屏。

这个工作本身可能只有：

```
1~5 ms
```

所以用户看到的第一帧就是正常 Markdown。

我现在对 **MDYe v0.1.0** 的定位已经比较明确了：

> **不是“再做一个 Markdown 编辑器”。**
>
> 而是先做一个类似图片查看器体验的 **Markdown 极速查看器**：
>
> **双击 → 几乎立即看到正文。**
>
> 哪怕是几十 MB 的 Markdown，也不等待全文解析完成。

这条路线，我认为比直接照着 mdview 再做一个 C++ 版本有意思得多。


我说：

> 也不需要做什么安装版本，用户即开即用最好，就是一个exe文件搞定，配置文件就同目录

可以，这样更符合 **MDYe** 的定位：**单文件、免安装、解压即用、零污染**。

我建议直接把“Portable First”定成硬约束。发布包甚至可以只有：

```
MDYe.exe
```

第一次运行后，如果用户确实改过设置，再在同目录生成：

```
MDYe.exe
MDYe.ini
```

或者：

```
MDYe.exe
MDYe.json
```

我更倾向 **INI**，因为配置很简单，人也能直接看懂和修改，例如：

```
[General]
Theme=System
Font=Microsoft YaHei UI
FontSize=16
MaxWidth=960

[Viewer]
RememberPosition=1
ShowOutline=1
WordWrap=1

[Performance]
FirstLoadKB=128
PreloadScreens=3
```

这样几个好处很明显：

- 不写 `%AppData%`
- 不写 `%LocalAppData%`
- 不创建服务
- 不需要 WebView2
- 不安装运行库
- 不需要管理员权限
- 不偷偷写一堆注册表
- 拷贝到 U 盘也能直接运行
- 删除整个目录就等于彻底卸载

编译上也要配合这个目标。我建议 **MSVC + 静态 CRT `/MT`**，第三方库也尽量静态链接进去。最终：

```
MDYe.exe
```

内部包含：

```
Win32 UI
Direct2D
DirectWrite
Markdown parser
图片解码
配置读写
```

Windows 自己带的系统 DLL 不算外部依赖，例如：

```
kernel32.dll
user32.dll
dwrite.dll
d2d1.dll
windowscodecs.dll
```

这些 Win10/Win11 都有，所以不需要随软件分发。

### 图片也尽量依赖 Windows 自带能力

这样不需要：


所以第一阶段应该非常纯粹：

> **MDYe v0.1 = 世界上打开 Markdown 尽可能快的 Windows 阅读器。**

把“双击立刻看到第一屏”先做成它最明显的特色。


我说：

> 图片也尽量依赖 Windows 自带能力  或者参考https://github.com/voidtools/voidImageViewer这个开源工具。

可以，而且我刚看了 `voidImageViewer`，这个项目非常值得我们参考它的“原生、轻量、少依赖”思路。

它本身就是纯 Windows 原生路线，仓库里直接有大量 C 源码，并且自己带了 `libwebp`，说明它也是优先利用系统能力，但对 Windows 原生不够稳定覆盖的格式，例如 WebP，再单独补一个很小的解码库。

所以 MDYe 我建议图片策略就这么定：

- PNG / JPEG / BMP / GIF / TIFF / ICO：优先走 **Windows Imaging Component（WIC）**
- SVG：第一版先不强求，可以占位显示；后面再评估 Direct2D SVG 或极小型解析器
- WebP：如果目标 Win10/11 环境里 WIC 支持不稳定，就像 `voidImageViewer` 一样，**静态集成精简版 libwebp**
- AVIF / HEIC：第一版不做，避免为了少量格式把依赖和复杂度拉上去
- 所有图片都异步解码，不允许阻塞首屏 Markdown

这样最终仍然可以保持：

```
MDYe.exe
```

一个文件搞定。

图片渲染链路我建议：

```
Markdown
   ↓
发现 ![](image.png)
   ↓
只读取图片尺寸/元信息
   ↓
先给正文预留区域
   ↓
首屏立即显示
   ↓
后台线程
   ↓
WIC / libwebp 解码
   ↓
转为 Direct2D Bitmap
   ↓
局部刷新
```

所以即使 Markdown 第一屏里放了一张 20 MB 的 PNG，也不能出现：

```
双击
↓
等图片解码
↓
白屏 1 秒
↓
正文出来
```

而应该是：

```
双击
↓
标题、正文立即出来
↓
图片位置先留白/占位
↓
几十毫秒后图片补上
```

这和我们前面定的 **First Screen First** 是完全一致的。

另外 `voidImageViewer` 还有一点很值得 MDYe 学：它甚至自己写了配置、INI、内存、OS 相关模块，而不是引入一个大框架；源码目录里就能看到 `ini.c`、\`mem.c\`、\`os.c\` 这些非常基础的模块。

所以我现在会把 MDYe 的原则定成：

> **能用 Win32 就不用框架，能用 Windows 系统组件就不带第三方库；确实缺失的能力，再静态集成一个足够小的库。**

当前技术栈我建议正式固定为：

```
MDYe
├─ C++20 / 少量 C
├─ Win32
├─ DirectWrite       文本
├─ Direct2D          绘制
├─ WIC               PNG/JPEG/GIF/BMP/TIFF/ICO
├─ md4c              Markdown 语法解析
├─ libwebp（可选）    WebP
├─ Memory Mapping    大文件
└─ INI               配置
```

**不采用：**

```
Qt
Electron
CEF
WebView2
Node.js
OpenCV
SDL
数据库
后台 HTTP Server
```

我认为这个方向现在已经很清楚了：**MDYe 不只是“小型 Markdown 阅读器”，而是按 Everything / voidImageViewer / EmEditor 这种 Windows 原生工具思路去做。**

下一步如果正式开始写代码，我建议 v0.1.0 第一刀就只做 6 件事：**单 EXE、命令行打开 md、极速首屏、标题/段落/粗体/代码块、滚动、本地图片异步显示**。其余功能一律后置。

## v0.1.0 · 从首屏设想做到 MDYe 原型

- **起点。** yakoye 对比 mdview 打开文档时短暂留白的体验，希望双击后像 EmEditor 一样马上看到内容，允许后续分段加载。他提出用 C 或 C++、先做浏览，并定名 MDYe。双方也讨论过设置项的边界，最终优先采用精简默认值、免安装的单 EXE 和同目录 INI。图片优先用 Windows 自带解码能力，只有系统能力不足时再考虑补充依赖。
- **当时的取舍。** 前文先把「打开第一眼看到正文」定为目标。讨论中的图片、全文搜索、目录和语法高亮可以逐步加载。原型阶段把阅读链路跑通，编辑涉及的输入法、插入符、选区、撤销和保存留给后续。
- **原型更新。** 旧包保留了 C++20/Win32、DirectWrite/Direct2D、文件映射和 WIC 方案。同步扫描文件前 128 KiB，后台建立全文块索引，按视口创建文字布局，本地图片后台解码。构建输出为单个 `MDYe.exe`，修改设置时才在同目录生成 `MDYe.ini`。
- **证据。** `MDYe-v0.1.0-source.zip` 的 README 将上述机制列为原型目标和实现方向。这里没有可复核的当年首屏性能测量结果。

## 衔接 v0.4.0 · 从实机反馈到逐块验收

以下记录共享聊天延伸到 v0.4.0 的讨论。完整版本条目见 [v0.4.0 至 v0.4.4 归档](https://github.com/yakoye/Shazao-markdown/blob/main/doc/archive/CHANGELOG-v0.4.4-v0.4.0.md)。

- **alpha1 与 editmode1。** 视频反馈之后，助手重新评估每块、每格各建 RichEdit 的方案，改回单一 DirectWrite/Direct2D 绘制表面，由一处管理光标和编辑。yakoye 随后把交互设计为明确的浏览／编辑状态，增加「打开文档后直接进入编辑模式」选项，取消双击切换，用右键「立即编辑／返回浏览」控制当前文档。
